# Public API Contract

The public consumer API is frozen for the required `version` integration surface:

- `SSH_Lib.Errors`
- `SSH_Lib.Clients`
- `SSH_Lib.Sessions`
- `SSH_Lib.Channels`
- `SSH_Lib.Known_Hosts`
- `SSH_Lib.Keys`
- `SSH_Lib.Config`
- `SSH_Lib.Git`
- `SSH_Lib.SCP`
- `SSH_Lib.File_Transfer`
- `SSH_Lib.SFTP`
- `SSH_Lib.Remote_Names`

## Status model

`SSH_Lib.Errors.Ok` is the only success status. Ordinary network, authentication, host-key, protocol, channel, timeout, and remote-exit failures return deterministic `Status` values instead of escaping as ordinary exceptions.

Expected mappings include `Invalid_Host`, `Invalid_Port`, `Invalid_User`, `Invalid_Command`, `DNS_Failed`, `Connection_Failed`, `Timeout`, `Handshake_Failed`, `Host_Key_Unknown`, `Host_Key_Mismatch`, `Authentication_Failed`, `Channel_Open_Failed`, `Channel_Request_Failed`, `Read_Failed`, `Write_Failed`, `Remote_Exit_Nonzero`, `Cancelled`, `Unsupported_Feature`, and `Internal_Error`.

## Session defaults

`Session_Options` keeps secure defaults:

- `Port = 22`
- `Connect_Timeout_MS = 30_000`
- `Read_Timeout_MS = 30_000`
- `Write_Timeout_MS = 30_000`
- `Verify_Known_Host = True`
- `Use_Agent = True`
- `Strict_Host_Key = True`

## Channel stream API

Channel I/O uses `Ada.Streams.Stream_Element_Array`. `Open_Exec` opens remote exec commands; `Open_Exec_With_Environment` sends an ordered `Environment_Variable_Array` before the exec request and fails closed if any server-side env request is rejected. `Open_Subsystem` opens SSH subsystems such as `sftp` and is the transport prerequisite for SFTP. `Open_Shell` opens a non-PTY shell channel through an authenticated session. `Open_PTY_Shell` first sends an RFC 4254 `pty-req` with caller-provided terminal type, columns, rows, optional pixel dimensions, and optional `Terminal_Mode_Array`, then opens the shell. Terminal modes are encoded as validated RFC mode opcode/value pairs and terminated by TTY_OP_END. `Resize_PTY` sends an RFC 4254 `window-change` request for active PTY shells. `Set_Environment` sends an explicit RFC 4254 `env` request with `want-reply` and returns `Channel_Request_Failed` when the server rejects it. `Request_X11_Forwarding` sends an explicit RFC 4254 `x11-req` request with `want-reply`; `Accept_X11` accepts one pending server-opened `x11` channel after setup. `Valid_X11_MIT_Magic_Cookie` validates the common 32-hex-character MIT-MAGIC-COOKIE-1 shape, and `X11_MIT_Magic_Cookies_Match` compares two such cookies case-insensitively. `Open_Direct_TCPIP` opens an RFC 4254 `direct-tcpip` channel to a target host/port through an authenticated SSH session; `SSH_Lib.Forwarding` supplies local and dynamic listeners, SOCKS5 CONNECT, one-connection SOCKS accept, callback accept services, managed worker-pool services, and bounded pump helpers for forwarding. `Accept_Forwarded_TCPIP` drains the protected session stream until one pending RFC 4254 `forwarded-tcpip` channel opened by the server is available, confirms it, and returns a normal binary channel for `Read_Some` and `Write`. `Read_Some` reads stdout/channel data, while `Read_Stderr` separately reads SSH extended-data type 1 for exec/shell diagnostics. `Read_Some`, `Read_Stderr`, and `Write` are binary APIs and must preserve NUL, LF, CR, DEL, bytes above 127, and arbitrary Git pkt-line, packfile, forwarded TCP, X11, diagnostics, shell, or SFTP bytes without UTF-8 validation, text conversion, or line-ending normalization.

`SSH_Lib.Forwarding` provides synchronous forwarding lifecycles: `Open_Local_Forward_Listener` binds and listens on a local TCP address for a fixed target, `Accept_Local_Forward` accepts one local client and opens the matching `direct-tcpip` SSH channel, `Open_Dynamic_Forward_Listener` binds a SOCKS listener, `Accept_Dynamic_Forward` accepts one local SOCKS client, reads a no-auth CONNECT request, opens the matching `direct-tcpip` SSH channel, sends the SOCKS reply, and returns the parsed target, `Read_Local`/`Write_Local` move bytes on the accepted local connection, and `Close` releases connection or listener resources. `Start_Local_Forward_Service` and `Start_Dynamic_Forward_Service` start callback-based background accept services that own bind/listen/accept/channel-open and call the supplied handler for each accepted local or SOCKS connection; their optional `Max_Accepted` cap stops the service after a bounded number of accepted connections. `Start_Managed_Local_Forward_Service` and `Start_Managed_Dynamic_Forward_Service` start managed local or SOCKS worker-pool services that own accept, channel-open, bounded pump, close, worker-count caps, and optional accepted-connection caps. `Managed_Forward_Service_Running`, `Managed_Forward_Service_Status`, `Managed_Forward_Service_Accepted_Count`, `Managed_Forward_Service_Completed_Count`, `Managed_Forward_Service_Active_Count`, `Managed_Forward_Service_Failed_Count`, `Managed_Forward_Service_Max_Concurrent`, `Managed_Forward_Service_Max_Accepted`, `Managed_Forward_Service_Bound_Port`, and `Managed_Forward_Service_Kind` expose managed lifecycle/status. `Stop`, `Forward_Service_Running`, `Forward_Service_Status`, `Forward_Service_Accepted_Count`, `Forward_Service_Max_Accepted`, `Forward_Service_Bound_Port`, and `Forward_Service_Kind` expose callback service lifecycle/status. It also exposes SOCKS5 no-auth CONNECT helpers: `Parse_SOCKS5_CONNECT_Request` for deterministic byte parsing, `Read_SOCKS5_CONNECT_Request` for accepted local connections, `Send_SOCKS5_Reply`, and `SOCKS5_Host`/`SOCKS5_Port` accessors for dynamic forwarding targets. X11 local display helpers parse `$DISPLAY`-style values with `Parse_X11_Display` or `Parse_X11_Display_From_Environment`; `X11_Display_Kind`, `X11_Display_Host`, `X11_Display_Port`, `X11_Display_Socket_Path`, `X11_Display_Number`, and `X11_Display_Screen` expose the resolved target, and `Open_X11_Display` opens a `Local_Forward_Connection` to either the Unix-domain X socket or TCP X display. `Pump_Once` moves one bounded chunk in one direction; `Pump_Bounded` alternates both directions for a caller-bounded number of iterations and reports per-direction byte totals. Callers still own X11 authorization policy and remote-forward fairness/cancellation policy. `Request_Remote_Forward` sends RFC 4254 `tcpip-forward` as a session global request and returns the bound port, including the server-allocated port when the requested port is `0`. `Cancel_Remote_Forward` sends `cancel-tcpip-forward`. SSH_Lib exposes local-forward, dynamic/SOCKS, X11 local-display, callback accept-service, managed worker-pool service, bounded pump, remote-forward request, cancel, and channel-accept primitives.

## File transfer scope

SFTP, SCP, and high-level file upload APIs are in scope. `SSH_Lib.SCP` builds shell-safe `scp -t -- '<path>'` upload commands, SCP regular-file headers, and can upload one regular-file byte array or streamed local file through either an already-open SCP sink channel or a session-level helper; streamed local-file uploads use at most `SSH_Lib.SCP.Upload_Chunk_Size` bytes per channel write. `SSH_Lib.File_Transfer` is the high-level upload facade: `Upload_Auto` and `Upload_SCP` route to SCP, while explicit `Upload_SFTP` routes byte-array and local-file uploads through SFTP; facade SFTP overloads with a filename upload to `Remote_Path/File_Name`, and the derived-name local-file overload uses the local path's simple name. Facade filenames are preflighted against `SSH_Lib.File_Transfer.Maximum_File_Name_Length`; facade SCP and `Upload_Auto` remote paths are bounded by `SSH_Lib.File_Transfer.Maximum_SCP_Remote_Path_Length`; facade SFTP composed paths are preflighted against `SSH_Lib.File_Transfer.Maximum_SFTP_Remote_Path_Length`; facade chunk-size aliases are exposed as `SSH_Lib.File_Transfer.SCP_Upload_Chunk_Size` and `SSH_Lib.File_Transfer.SFTP_Upload_Chunk_Size`.

`SSH_Lib.File_Transfer` also exposes first-class exact-path workflows: `Upload`, `Verify`, `Delete`, `Restore`, and `Inventory`. These are SFTP-backed workflow APIs returning `Workflow_Result` or `Inventory_Result`, so applications can use named backup/file-management operations without manually composing lower-level `Upload_File`, `Download_Directory`, `Remove_Tree`, `Stat`, `Check_File`, and `List_Directory` calls. `Upload` writes a local file to the exact remote path or a local directory to the exact remote root; `Restore` downloads a remote file or directory to the requested local path and accepts `Overwrite_Existing`, `Skip_Existing`, or `Fail_If_Exists`; `Delete` supports file, directory, tree, and auto-detected removal; `Verify` checks remote existence/size and optionally uses the SFTP `check-file` extension. `Inventory` opens one SFTP client for recursive traversal and returns one entry or a recursive manifest-style vector with paths, kinds, and SFTP attributes, while `Inventory_With_Checks` additionally records per-file `check-file` digest algorithm and digest bytes. `Inventory_Manifest` serializes that vector to the line-oriented `SSH_LIB_INVENTORY` format with escaped paths and optional digest columns; `Parse_Inventory_Manifest` reads current digest-aware manifests and legacy v1 manifests. `Verify_Inventory` compares a current remote tree to a manifest and automatically uses `Inventory_With_Checks` when the manifest contains digests. `Restore_From_Inventory` / `Restore_From_Manifest` restore manifest-described regular files and directories under a local root; symlink entries are parsed and inventoried but local symlink restoration is currently reported as `Unsupported_Feature`.

`SSH_Lib.SFTP` provides packet framing, the SFTP v3 init/version handshake, byte-array upload, streamed local-file upload, in-memory and local-file download, directory listing, `stat`/`lstat`, permission updates, mkdir/rmdir/remove/rename, and symlink/readlink helpers over an `sftp` subsystem channel; uploads send at most `SSH_Lib.SFTP.Upload_Chunk_Size` data bytes per `SSH_FXP_WRITE` request. Callers can also stream bytes through explicit remote exec channels, including Git `receive-pack` flows built with `SSH_Lib.Git`.

## No C or subprocess dependency

The public API does not require C bindings, C sources, OpenSSL/libcrypto/libsodium hidden bindings, subprocess ssh fallback, or shell execution.

## SSH_Lib.Git_Transport

`SSH_Lib.Git_Transport` is an optional narrow helper for `version`-style consumers. `Prepare` parses a remote name, resolves SSH config using the parsed host as lookup key, applies explicit remote user/port overrides, preserves host-key verification defaults, and builds either an upload-pack or receive-pack exec command.

`Open_Service` opens the prepared upload-pack or receive-pack exec channel on an already-authenticated session. `Complete_Service` writes a caller-built request, sends SSH EOF, drains stdout into a caller-provided bounded response buffer, validates the upload-pack response or receive-pack report shape, attempts remote exit-status observation, closes the channel, and returns `Git_Workflow_Summary` counts, parsed response summaries, and whether exit status was observed. `Run_Service` combines those steps for callers that want a single blocking service exchange.

It does not authenticate by itself, store objects, update refs, maintain object/ref databases, choose negotiation policy, store credentials, or invoke local subprocesses.

`SSH_Lib.Config.Has_Unsupported_Feature` is retained for API compatibility; current route dependencies parsed by the config layer are supported. `ProxyJump` is resolved as data in `Session_Options.Proxy_Jump` and `Sessions.Open` routes it through an SSH `direct-tcpip` jump channel. `ProxyCommand` is resolved as data in `Session_Options.Proxy_Command` and `Sessions.Open` routes SSH over the configured subprocess transport. The OpenSSH sentinel `ProxyCommand none` disables the proxy command instead of executing a command named `none`. The subprocess transport applies configured read/write timeouts to ProxyCommand pipes and uses `Connect_Timeout_MS` as the fallback pipe timeout when read/write timeouts are unset.

`ControlMaster`, `ControlPath`, and `ControlPersist` config directives are parsed and resolved as session data in `Session_Options.Control_Master`, `Control_Path`, and `Control_Persist`.

`LocalForward`, `RemoteForward`, and `DynamicForward` config directives are parsed and resolved as line-separated session data in `Session_Options.Local_Forwards`, `Remote_Forwards`, and `Dynamic_Forwards`. `SSH_Lib.Config_Apply.Start_Configured_Local_Forwards` and `Start_Configured_Dynamic_Forwards` start managed local/dynamic services from those values, and `Request_Configured_Remote_Forwards` sends the configured remote-forward requests.

`SendEnv` and `SetEnv` config directives are parsed and resolved as line-separated session data in `Session_Options.Send_Env` and `Set_Env`. `SSH_Lib.Config_Apply.Apply_Configured_Environment` applies those values to a caller-supplied channel with RFC 4254 `env` requests.

`SSH_Lib.Security_Keys` exposes direct hardware-backed SK userauth integration without requiring ssh-agent. Callers provide a `Security_Key_Signer` callback that receives the exact SSH publickey payload to sign plus the application string, public-key algorithm, and public-key blob. `Build_Signed_Request` encodes the resulting OpenSSH signature blob into an SSH `USERAUTH_REQUEST` for `sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`, or compatible certificate algorithms selected by the caller.


### Phase 18 direct remote/config composition helpers

`SSH_Lib.Remote_Names.Has_Explicit_Port (Remote_Text)` reports whether the original `ssh://` remote text included an authority port. This lets callers distinguish implicit default port 22 from an explicit `:22` override.

`SSH_Lib.Config.Resolve_Remote (Config, Remote_Text, Default_User, Options)` parses and resolves the original remote text in one step, applies explicit remote user and explicit remote port overrides over config values, preserves host-key verification defaults, preserves `ProxyCommand` and `ProxyJump` as session data, and returns `Invalid_User` when no remote/config/default user is available. It does not open a network connection or parse Git protocol data. The text-aware overload also reports NUL, CR, or LF in the repository-path portion as `Invalid_Command`, matching `SSH_Lib.Git_Transport.Prepare` for direct version-style composition.
